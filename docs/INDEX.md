ADR-031 now collects three findings about tools reporting state misleadingly, the third being a manual volume snapshot with `expiresAt: null` that disappeared anyway, mechanism unknown — recorded for its consequence: a manual snapshot is not reliable insurance before a risky operation. Sprint 14 opens with ADR-040 (the Portal ships in English only — Lithuanian is sequenced rather than dropped, because it is the *terminal* that needs it; every string goes through a dictionary from day one, a decision about order rather than scope), ADR-041 (Playwright runs only on PRs touching the frontend — not to save minutes, but because a slow check that runs on everything gets worked around, and a bypassed check is worse than an absent one), and ADR-042 (rate-limit state moves to Redis and fails open with a once-per-outage alert — ADR-028 had recorded the per-process counter as a property, and re-read it is a defect: with two instances the documented 10/min silently becomes 20/min, so the mechanism's correctness rested on an infrastructure fact recorded in no document). ADR-031 gains a fourth finding that generalises the other three: a claim about someone else’s code lives until its first execution, not until its first review — two confident, wrong statements in one week (Stripe’s v1 calls, and controller-level throttle budgets), both caught by running something rather than re-reading anything. ADR-043 closes a confirmed data leak and names its shape: the guard asks whether the caller holds a permission on ANY Membership, a list builds its scope from EVERY Membership, and nothing asks whether those are the same one — a zero-permission Waiter exported another restaurant’s transaction rows until `permittedScope` landed. Its most durable finding is not the leak: five existing tests had encoded it as the specification, three of them built on fixtures describing users the seed cannot produce. ADR-044 gives `roleId` a source at last (`GET /roles` — a required input that nothing returned for ten sprints) and closes what building it exposed: `Administrator` holds every Permission and any restaurant Owner could grant it, because every write path validated only that the id existed. Fixed as a column rather than a filtered dropdown — a filtered interface over an endpoint that accepts anything is the failure mode where the screen looks correct and the API is not. The doors were counted by grepping for the field, which found four where reasoning had found two. ADR-045 answers, as a measured fact rather than a plan, what production did with an error nobody caught: inside HTTP it was logged completely and read by nobody; outside HTTP there was no handler at all, so a rejected promise in a money job killed the process, Railway restarted it, and the trace died with it — *"a service crashing and restarting in a loop looks, from outside, exactly like a service that is working."* Closed with our own AlertService before any vendor, because the policy (what is one incident, how often may it speak, which fields may leave) is the part that matters and the part that is ours. Its dedup state stays in memory *because* ADR-042 moved rate limiting out of it — a limiter's correctness is the count, a deduplicator's is not — recorded explicitly so the precedent is not applied by resemblance. Carries an addendum to ADR-044 explaining why `roleId` was the outlier: it was the one dangerous input the API accepted but never emitted, so nothing ever defined its legitimate range and four write paths independently settled for "does the id exist". The predictive form — look for inputs accepted but never returned. ADR-046 makes the seed reconcile RolePermission instead of only adding to it — a Permission removed from seed.ts used to survive forever on any existing database, which is ADR-044's platform_only failure with the direction reversed. Falsified on a populated database rather than through db:reset, which proves nothing here because a rebuilt-from-empty database cannot distinguish "only adds" from "reconciles". Production measured by permission NAME rather than count and found exactly in sync (0 revocations, 0 grants) — and deliberately not written to, because whether the seed should run at all is the decision still open. Its consequence is stated rather than buried: running the seed is now strictly more dangerous, which makes automating it both more necessary and more dangerous at once. |

| [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md) | 1.2.0 | **Part 1** — the design decisions that survive a change of palette: the Dashboard's emotional contract ("today is a good day" — an answer to *how are we doing?*, not *is anything wrong?*), the Hierarchy Law that ranks elements by meaning-per-second rather than by data volume, how a figure carries a caveat it cannot be honest without (ADR-026's `todayRevenueNote`), and — promoted here to a first-order product requirement — the zero state, because a screen designed to convey "today is a good day" conveys the opposite far more forcefully when the figures are zero. Names three distinct zero states and the mirror risk of making them all reassuring — reassurance comes from explanation, never suppression, or a real outage becomes indistinguishable from a quiet morning. Two rules bind Part 2 before it is written: accent colour never carries importance (size and space do, and the test is whether the hierarchy survives the accent being removed), and the customer terminal shares the Portals' foundation but chooses its own surface treatment — because on that one surface the user is not ours, gets ten seconds, and has no reason to try again. The accent must also be a token from the first line of CSS, never a literal: the deferred terminal-branding candidate (`MASTERPLAN.md`) needs exactly one swappable accent, which is free to build in now and a sweep of every component to retrofit — semantic colour is never customisable, because a failed payment must look failed in every restaurant. **Product Identity On Screen** (v1.1.0) — the product is PlainTabs, the wordmark is typographic and never the accent, it is the rank-1 element on every screen reachable before authenticating, and it is absent from the terminal payment step because a guest needs to trust the restaurant rather than us. Found by the Founder when the first login screen shipped without a name: the gap was this document’s, not the screen’s. Records the distinction that stops someone “filling in” a correctly sparse screen — sparseness is right, a missing name is a missing element. **Part 2** — the visual layer, written to one standard: *measured, or it does not exist*. Three surfaces (light Portal by default, dark as preference, pure-white terminal for sunlight), a warm-neutral ramp, one accent token with five verified values (default `#9A5D14`, and the record notes plainly that the default is the weakest of its own set at 5.19:1), a reserved semantic pair, **no warning colour at all** — deliberately, since the two places one would be used are the two Part 1 forbids alarming — IBM Plex Sans with mandatory tabular figures, and the Hierarchy Law made numeric so a review can fail on arithmetic rather than opinion. Carries one visible retraction — the dark-Portal justification, withdrawn after it turned out to cite a room no document describes and a screen this product does not have — and two transcription corrections found only by turning the tables into code: the 0.62 hierarchy constant forbade its own example (30 ÷ 48 = 0.625), and `--rule` pointed at a value that was not on the ramp at all. | [PERSONAL_DATA_MAP.md](PERSONAL_DATA_MAP.md) | 1.0.0 | A factual inventory of every field identifying a person, what it links to, and what breaks if it is removed — research only, no decisions. Written because two Stripe obligations found in Sprint 14 (our own terms referencing the Connected Account Agreement, and a privacy policy linking Stripe's) both depend on knowing the answer. Its central structural finding: the boundary between "a person" and "a subject of a financial record" already runs at Membership.id, because every financial reference points at a Membership and never at a User — so the apparent conflict between erasure and the Ledger is not real. The conflicts that ARE real: AuditLog.user_id is ON DELETE SET NULL, so deleting a User blanks its own audit trail; displayName is load-bearing for three presentation joins; and AuditLog.metadata is unbounded Json, the one field where personal data can accumulate with nobody deciding it should. And the fact that matters most: soft delete is written by exactly one code path in the backend (Restaurant), so nothing ever sets deletedAt on a User or Membership — a GDPR erasure request has no code path at all. |
